Proposta de solução — Recuperação automática de acesso do corretor

1. Cenário atual

Atualmente, existe uma dificuldade no processo de recuperação de acesso dos corretores à plataforma.

Considerando a regra de negócio de que o usuário fica inativo após 6 meses sem realizar login, o corretor pode tentar acessar a plataforma após esse período e não conseguir prosseguir normalmente.

Nesse cenário, a recuperação do acesso acaba dependendo de intervenção manual de pessoas responsáveis pelo atendimento, gerando:

  • abertura de chamados;
  • trabalho operacional;
  • dependência de outras pessoas para uma atividade simples;
  • aumento do tempo para o corretor recuperar o acesso;
  • custo operacional desnecessário.

Além da questão técnica, existe uma deficiência de processo. Uma atividade que pode ser realizada de forma automatizada e self-service está sendo tratada manualmente.

2. Regra de negócio considerada

Para esta proposta, será considerada a seguinte regra:

Um usuário será considerado inativo quando estiver há mais de 6 meses sem realizar login na plataforma.

A tabela de usuários já possui a informação referente ao último acesso:

USUARIO
-------------------------
ID
CPF
EMAIL
STATUS
ULTIMO_LOGIN

Exemplo:

ULTIMO_LOGIN = 2026-01-10

Se o usuário tentar acessar a plataforma em:

2026-07-11

ele estará há mais de 6 meses sem realizar login e deverá entrar no fluxo de recuperação de acesso.

3. Solução proposta

A proposta é utilizar a própria tentativa de login para identificar automaticamente essa situação.

POST /login | v Busca usuário | v Verifica último login | +---- Usuário ativo | | | v | Login normal | +---- Mais de 6 meses | v Retorna situação específica | v Front-end redireciona para recuperação de acesso

4. Alteração no backend

Durante o processo de login, o backend deve consultar o usuário e verificar a data do último login.

LocalDateTime limitDate = LocalDateTime.now().minusMonths(6);

if (user.getLastLogin() == null ||
    user.getLastLogin().isBefore(limitDate)) {

    throw new UserInactiveException();
}

O ideal é retornar um código de negócio específico para que o front-end saiba exatamente qual fluxo deve executar.

HTTP/1.1 403 Forbidden

{
    "code": "USER_INACTIVE",
    "message": "User inactive due to inactivity period."
}

5. Comportamento do Front-end

Ao receber o código USER_INACTIVE, o front-end deve direcionar o corretor automaticamente para uma tela de recuperação de acesso.

if (response.code === "USER_INACTIVE") {
    redirect("/recover-access");
}

6. Fluxo de recuperação

Usuário tenta realizar login | v Sistema identifica usuário inativo | v Front-end direciona para "Recuperar acesso" | v Usuário informa seus dados | v Sistema valida o usuário | v Gera código temporário | +--------> E-mail | +--------> WhatsApp | v Usuário informa o código | v Sistema valida o código | v Permite definir nova senha | v Usuário é reativado | v Novo login

7. Geração do código

O código deve ser temporário e possuir validade limitada.

String code = generateRandomCode();

recoveryCodeRepository.save(
    RecoveryCode.builder()
        .userId(user.getId())
        .code(hash(code))
        .expiresAt(LocalDateTime.now().plusMinutes(10))
        .build()
);

O código original deve ser enviado ao usuário por um canal previamente validado, como e-mail ou WhatsApp.

O banco deve armazenar preferencialmente apenas o hash do código.

8. Validação do código

POST /users/recovery/verify-code
{
    "user": "12345678900",
    "code": "834921"
}
RecoveryCode recoveryCode =
    recoveryCodeRepository.findValidByUserId(userId);

if (!matches(code, recoveryCode.getCode())) {
    throw new InvalidRecoveryCodeException();
}

if (recoveryCode.getExpiresAt().isBefore(LocalDateTime.now())) {
    throw new ExpiredRecoveryCodeException();
}

9. Redefinição da senha

POST /users/recovery/password

{
    "recoveryToken": "...",
    "newPassword": "********"
}
  1. validar o token de recuperação;
  2. validar as regras da nova senha;
  3. atualizar a senha;
  4. reativar o usuário;
  5. invalidar o código/token utilizado;
  6. registrar a operação em log/auditoria.
user.setPassword(passwordEncoder.encode(newPassword));
user.setStatus(UserStatus.ACTIVE);

userRepository.save(user);

recoveryTokenService.invalidate(token);
auditService.register("USER_ACCESS_RECOVERED", user.getId());

10. Atualização do último login

Após um login realizado com sucesso, o sistema deve atualizar a data do último login.

UPDATE USUARIO
SET ULTIMO_LOGIN = CURRENT_TIMESTAMP
WHERE ID = :userId;

Não deve ser registrado o código de recuperação ou a senha em texto puro.

12. Resultado esperado

Com essa alteração, o processo deixa de ser:

Corretor ↓ Não consegue acessar ↓ Procura atendimento ↓ Abre chamado ↓ Pessoa analisa ↓ Pessoa realiza procedimento ↓ Corretor recupera acesso

E passa a ser:

Corretor ↓ Tenta acessar ↓ Sistema identifica inatividade ↓ Front-end direciona para recuperação ↓ Código por e-mail/WhatsApp ↓ Validação ↓ Nova senha ↓ Usuário reativado ↓ Acesso liberado

13. Ponto principal da proposta

A principal melhoria não é apenas implementar uma nova API ou uma nova tela.

É revisar o processo atual e retirar uma atividade operacional que pode ser realizada pelo próprio usuário.

O sistema já possui uma informação importante — a data do último login. Essa informação pode ser utilizada para identificar automaticamente usuários inativos e iniciar um fluxo seguro de recuperação.

Dessa forma, a solução atua simultaneamente em três pontos:

PROCESSO ↓ Menos intervenção manual SISTEMA ↓ Identificação automática da inatividade USUÁRIO ↓ Recuperação de acesso self-service

O objetivo final é reduzir o volume de atendimento, diminuir o tempo de recuperação do acesso e eliminar uma etapa operacional que não precisa depender de intervenção humana.
